# Technical Solution Rules

## Purpose

生成能够支持研发评审、开发落地和技术复盘的 Markdown 技术方案。内容必须贴合实际项目和后端研发场景，避免空洞描述。

## Content Standards

- 结构规范，逻辑清晰，描述具体。
- 使用正式、专业、可执行的技术表达，避免口语化。
- 说明业务背景、需求目标、核心问题、适用场景和业务价值。
- 说明整体技术思路、设计原则、核心实现逻辑和架构思路。
- 详细说明接口、功能、数据和配置的新增、修改、废弃或无变更情况。
- 工作量预估必须列出预计修改的后端文件、模块、修改内容和合理的代码量区间。
- 测试方案必须覆盖测试重点、主要场景、边界测试、回归范围和验证标准。
- 已确认问题需要说明背景和处理方式。
- 待确认问题需要说明问题描述、产生原因、影响、建议处理方式、建议理由以及是否需要业务确认。
- 所有章节都必须存在；无内容时写明“无”并解释判断依据。

## Scope Rules

- 默认只分析后端实现。
- 不将前端、客户端、测试代码、测试执行和其他非后端工作量计入工作量。
- 仍然要在测试方案中说明后端测试范围。
- 需要读取实际代码、配置、接口定义、数据模型和相关文档后再做文件级判断。

## Reliability Rules

- 不能把推测写成事实。
- 不能编造不存在的文件、接口、类、表、字段或业务规则。
- 无法确认的内容放入“待确认问题”。
- 代码量只能给出基于实际分析的合理估算区间，并说明估算依据。
- 不能因为需求简单而删除固定章节。
- 不能只写“修改相关代码”“增加校验”“完善逻辑”等不可执行描述。

## Markdown Rules

- 使用标准 Markdown 标题层级。
- 一级标题用于方案标题，二级标题用于固定章节，三级标题用于章节内分组。
- 使用 Markdown 表格表达文件清单、接口变更和工作量等可比较内容。
- 使用代码块表达接口示例、字段示例或关键伪代码。
- 重点内容可适当加粗，但不要大面积加粗。
- 保持段落、列表、表格和代码块之间的空行。
